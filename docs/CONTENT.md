# Content

Section 7 of the kit. The case file format below is the case JSON schema. When P2 adds the zod schema in code, that schema and this file must agree, and `npm run content:check` enforces it.

### Case file format

Cases live in `content/cases/*.json` and are validated by zod and `content:check`:

```
id, slug, title, track ("consulting"), type (profitability | market_entry | market_sizing | m_and_a |
pricing | growth | operations | other), industry, difficulty (1–3), style (interviewer_led | candidate_led),
est_minutes, prompt, facts[] {question_topic, answer},
structure_rubric {key_buckets[], good_signs[], red_flags[]},
exhibits[] {id, title, kind (table | bar | line), data {columns[], rows[][]}, reveal_hint, insight},
math[] {id, question, inputs {name: number}, expression, expected, tolerance_pct, working},
brainstorm {question, idea_bank[]}, synthesis_rubric {must_mention[], good_signs[]},
model_answer_outline (paid), free_starter (bool), free_preview (bool),
status (draft | reviewed), reviewed_by, reviewed_on
```

### Tests (`content:check`)

- Every `math.expected` must equal `expression` evaluated with `inputs`, within `tolerance_pct`.
- Exhibit numbers that the maths relies on must match the inputs.
- Slugs and IDs must be unique.
- Only `status: "reviewed"` cases are shown to users. Drafts stay hidden.

### Launch targets

- **20 original cases:** at least 2 of each type, with 1 marked `free_starter` and 3–5 marked `free_preview`.
- **300+ drills:**
  - mental maths drills generated by code
  - market sizing prompts with model approaches
  - framework drills
  - chart-reading drills using generated charts

### Writing rules

- Original, realistic but **invented** companies and numbers.
- A mix of US and UK settings.
- Numbers that work well for mental maths.
- Write in plain English.
- Each case must have a clear "right answer zone".

### Review

The founder or a paid reviewer with consulting experience reads each case before it is set to `reviewed`. Claude Code writes the drafts and runs `content:check`. A human approves.

### Guides

Guides are factual and cite their sources. Firm-specific facts come only from official career pages (rule 2.2).

## How the content engine works (added in P2)

This section records decisions made while building milestone P2. Where it adds to the kit's case format above, the addition is optional and backwards compatible.

### Adding or changing a case

1. Write `content/cases/<slug>.json` (the file name must equal the `slug`). Start it as `"status": "draft"`, `"reviewed_by": null`, `"reviewed_on": null`.
2. Add it to the list in `lib/content/all-cases.ts`. (Cases are bundled into the app rather than read from disk at run time; a test fails if a file is missing from the list.)
3. Run `npm run content:check`. It validates the format and **recomputes every maths answer and every exhibit number the maths relies on** (rule 2.9).
4. A human with consulting experience reads the case. Only then is `status` changed to `"reviewed"` and `reviewed_by` and `reviewed_on` filled in. **Claude Code never sets a case to reviewed.**

### Additions to the case format

- `math[].input_sources` (optional): `[{ "input": "profit_last", "exhibit_id": "pl-per-cafe", "row": 5, "column": "Last year" }]`. It says which exhibit cell an input came from, and `content:check` fails if the number in the exhibit and the number in `inputs` disagree. Use it for every input that comes from an exhibit.
- Numbers in `inputs` and `expected` must be exact. `content:check` accepts a difference of at most 0.01% (for rounding such as 66.6667), which is stricter than the kit's `tolerance_pct`. `tolerance_pct` is how close a candidate's answer must be.
- Expressions may use numbers, named inputs, `+ - * / ^` and brackets, nothing else (`lib/content/expr.ts`).

### What visitors see

- **Everyone:** the title, type, industry, difficulty, length and the **prompt** (the first stage).
- **`free_preview` cases also show their first exhibit's data**, never its `insight`. Everything else is locked behind the AI interview: facts, rubrics, the rest of the exhibits, the maths, the idea bank and the model answer.
- The public view is an allow-list in `lib/content/public.ts`. `tests/content-public.test.ts` checks that no answer-key text from any case can reach a browser, and the browser test checks the real page HTML.

### Draft visibility

`status: "draft"` cases are hidden from real visitors. They are shown only where `SHOW_DRAFT_CONTENT=1`: Vercel **Preview** deployments (already set) and local work. **Never set it for Production.** Draft pages carry a visible "Draft case" notice. On the live site `/cases` shows "Cases are being checked" until at least one case is reviewed.

### Drills

- **Generated by code** (`lib/drills/`): 240 mental-maths drills (12 families x 20) and 60 chart-reading drills (4 families x 15). They use a seeded random generator, so ids and answers never change. Each records the expression it came from, and `tests/drills.test.ts` recomputes every answer with the safe evaluator; chart answers are re-derived from the plotted points.
- **Hand-written** (`content/drills/`): 12 market-sizing estimates (answers computed from their stated assumptions) and 16 framework multiple-choice questions. The files list the right framework option first; the loader shuffles the options the same way every time.
- **Answers stay on the server.** The browser receives questions only; `checkDrill` (a server action) marks the answer. Logged-in free users are limited to `siteConfig.limits.free.drillsPerDay` attempts a day (counted from `drill_attempts`); visitors without an account get a soft limit of `siteConfig.limits.anonymous.drillsPerSession` per browser tab.
- Total today: 328 drills. The launch target is 300+.
